# PALANART: восстановление регистрации, 26 октября 2026

## Фактический статус

Исправления клиентского кода опубликованы на https://palanart.github.io/user.html.
Полностью рабочая регистрация **не подтверждена**: домен настроенного backend
`jioakguorsfvjuzyclrg.supabase.co` возвращает DNS NXDOMAIN (проверено также через
Cloudflare DNS over HTTPS). Подключённый Supabase показывает пустой список проектов;
запрос этого project ref возвращает отказ в доступе. В доступной организации нет этого проекта.
Это не доказывает отсутствие проекта у другого владельца: нужны актуальные данные/доступ.

Ни SQL, ни новые Edge Functions в production Supabase не применялись. Работоспособность
SMTP, реальных аккаунтов и провайдерских ключей проверить невозможно без backend.

## Что исправлено

| Сценарий | Было неисправно | Исправление | Полный реальный тест |
| --- | --- | --- | --- |
| Регистрация e-mail | Локальные пароли; регистрация без реальной Auth-сессии; подтверждение ошибочно открывало кабинет | Только Supabase Auth; проверка всех полей; дубликаты; подтверждение без преждевременного входа | ТРЕБУЕТ НАСТРОЙКИ: backend недоступен |
| Вход e-mail | Проверка пароля в localStorage; нет защиты повторной отправки | Серверная проверка пароля и токена; состояния загрузки; повторные отправки блокируются | ТРЕБУЕТ НАСТРОЙКИ: backend недоступен |
| Восстановление | Не было формы/обработки recovery | Запрос письма, обработка recovery-сессии, новый пароль, проверка ошибок и интервал отправки | ТРЕБУЕТ НАСТРОЙКИ: SMTP и backend не проверены |
| Telegram | Фиктивный локальный аккаунт; недостаточная привязка state к браузеру | Настоящий виджет; серверная HMAC-проверка, срок действия, одноразовый state и HttpOnly cookie | ТРЕБУЕТ НАСТРОЙКИ |
| VK ID | Фиктивный вход; PKCE verifier раскрывался в подписанном state; недоверенные JWT claims | Серверный code exchange; приватный verifier; профиль через API VK; одноразовый callback | ТРЕБУЕТ НАСТРОЙКИ |
| MAX | Не было backend; фиктивный локальный аккаунт | Мини-приложение, проверка подписи initData, отдельный секрет исходного браузера, подтверждение имени перед выдачей сессии | ТРЕБУЕТ НАСТРОЙКИ |
| Яндекс ID | Не было backend; фиктивный локальный аккаунт | OAuth code + PKCE; серверный обмен токена и запрос профиля | ТРЕБУЕТ НАСТРОЙКИ |
| Город/формы | Нет полной валидации и устойчивой обработки ошибок | Список и свободный ввод; таймаут геолокации и геокодирования; понятные ошибки | РАБОТАЕТ: ручной ввод и интерфейс; реальный GPS не подтверждён |

Новые пароли не сохраняются в базе браузера. Идентификатор кэша кабинета связывается
с подтверждённым `auth.users.id`. Старые browser-only записи и история не сбрасываются.
После успешного входа с тем же e-mail старая запись сохраняет свой локальный id,
избранное и связи; её устаревший локальный пароль удаляется. Старый локальный пароль
никогда не используется как доказательство владения серверным аккаунтом.

При проверке публикации обнаружена и устранена загрузка старого кешированного
auth-bridge вместе с новой страницей. Адреса ресурсов авторизации версионированы,
протокол между модулями проверяется, устаревшая версия не может вызвать фиктивный вход.

Привязка нового социального способа запускается из существующего кабинета и требует
проверенного JWT. Совпадение неподтверждённого e-mail не объединяет аккаунты.
Для нового социального аккаунта используется стабильный subject провайдера и реальная
Supabase-сессия. Синтетический внутренний адрес не является почтовым ящиком.
Email-first аккаунт можно привязать к любому из четырёх социальных способов.
Отдельная смена внутреннего адреса social-first аккаунта на почтовый адрес в этой работе
не реализована; автоматическое объединение уже разных аккаунтов также не выполняется.

## Что требуется от владельца

1. Восстановить доступ к существующему Supabase-проекту или указать его актуальный ref/URL.
   Подключить именно этот проект к Supabase в Codex. Секреты в чат или публичный репозиторий не передавать.
2. Проверить состояние проекта и существующие таблицы, логи, security/performance/health advisors.
   Получить полный резервный снимок данных, включая `auth` и необходимые прикладные схемы.
3. В Auth включить Email, подтверждение адреса, минимальную длину пароля 10 и правила сложности.
   Настроить рабочий production SMTP, отправителя, ограничения частоты и антибот-защиту.
   Проверка в форме дополняет, но не заменяет серверную политику паролей.
4. Site URL: `https://palanart.github.io/`. Разрешить точные redirects:
   - `https://palanart.github.io/user.html`
   - `https://palanart.github.io/user.html?recovery=1`
   - `https://palanart.github.io/artist.html`
   Старые адреса `ivan19326.github.io/palanart-marketplace-app/` добавлять только если
   старая публикация продолжает использоваться. Не разрешать произвольные домены.
5. После исследования схемы проверить и применить `supabase/sql/auth-hardening.sql`
   в транзакции. Это deployment draft, **не применённая миграция**. Затем оформить
   миграцию штатным CLI. Скрипт добавляет профили с RLS, служебные одноразовые попытки
   и уникальные связи provider/subject → существующий `auth.users.id`.
   Профиль читается/редактируется только владельцем; роли, e-mail и провайдеры
   нельзя менять через клиентскую запись. Служебные таблицы доступны только service_role.
   Привилегированный trigger находится в закрытой схеме и не доступен как публичный RPC.
6. В Edge Function Secrets задать переменные из `supabase/functions/.env.example`.
   Существующие service_role credentials использовать только на сервере.
   Включить ограничения частоты запросов к публичным start/callback/claim endpoints.
7. Развернуть девять функций командой `npm run supabase:functions:deploy`.
   У публичных входных точек `verify_jwt=false`: проверка JWT при привязке, подписей
   провайдеров и одноразовых state выполняется в коде функций. CORS ограничен
   `ALLOWED_RETURN_ORIGINS`; cookies Secure/HttpOnly; ответы Auth не кешируются.
8. После изменений запустить Supabase advisors и реальную проверку RLS с anon,
   владельцем профиля и другим пользователем. Подготовленный SQL ещё не проверен
   на действующей структуре базы.

### Настройки провайдеров

Общий callback-префикс, если восстановлен прежний project ref:
`https://jioakguorsfvjuzyclrg.supabase.co/functions/v1/`.
Если ref изменился, заменить URL/publishable key в `auth-config.js` и параметры
серверной конфигурации; сохранить и перенести прежние аккаунты с их UUID.

| Провайдер | Настройки | Callback/точка входа |
| --- | --- | --- |
| Telegram | Владение ботом, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`; BotFather `/setdomain` → `palanart.github.io`; проверить фактическое владение PalanAuthBot | `auth-telegram-callback`; виджет на `/telegram-login.html` |
| VK ID | Web-приложение, `VK_CLIENT_ID`; `VK_CLIENT_SECRET` для confidential app при необходимости; разрешённые домены сайта и callback, доверенный Redirect URI | `auth-vk-callback` |
| MAX | Зарегистрированный бот/мини-приложение; `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`; URL мини-приложения `https://palanart.github.io/max-login.html` | `auth-max-callback` + `auth-max-claim`; открытие `https://max.ru/<bot>?startapp=<state>` |
| Яндекс ID | Приложение для авторизации; `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`; права `login:info`, `login:email`, при необходимости `login:avatar` | `auth-yandex-callback` |

MAX подтверждает личность в отдельном webview. В исходной вкладке пользователь
нажимает «Проверить подтверждение MAX», сверяет имя и подтверждает повторным нажатием.
До этого не создаётся Auth-пользователь, не привязывается идентичность и не выдаётся сессия.

## Проверки

`npm run test:auth` — 20 автоматических проверок реального кода с тестовыми
адаптерами Auth/БД: валидация, подтверждение, дубликаты, повторный вход/выход,
сохранение legacy-истории, недоверенная сессия, ошибки пароля, recovery,
сохранение админ-сессии, PKCE VK/Яндекс, подписи/сроки/дубликаты Telegram/MAX,
повторное использование state, CORS, защита привязки и гонка выхода.
Эти проверки **не являются реальным OAuth-тестом** внешних аккаунтов.

В браузере проверены: поля, ошибка телефона, переходы к входу/регистрации,
открытие восстановления, ввод произвольного города, загрузка и сетевая ошибка,
мобильная ширина 390 px без горизонтального переполнения; корректный возврат к
ручному вводу при недоступной геолокации. Первая сборка и публикация GitHub Pages
успешны. Финальная публикация `084ee51` также успешно развёрнута; исходники `79e33f8` прошли проверки в CI.

После восстановления backend обязательны: новый контролируемый e-mail → письмо →
подтверждение → кабинет → выход → повторный вход; неверный пароль; дубликат e-mail;
recovery-письмо → новый пароль → вход; четыре реальных провайдера, отмена входа,
повторный callback, привязка к уже существующему аккаунту и отсутствие дублей;
десктоп/телефон, геолокация при разрешении и отказе, регрессии каталога,
кабинета исполнителя и админ-панели. Реальные test-аккаунты и SMTP ещё не предоставлены.
