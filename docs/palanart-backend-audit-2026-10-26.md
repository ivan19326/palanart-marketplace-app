## Варианты восстановления существующего проекта

### Dashboard показывает Paused

Убедиться, что ref равен `jioakguorsfvjuzyclrg`. Использовать **Resume project**
для этого существующего проекта. По актуальной документации Supabase восстановление
приостановленного проекта доступно в течение **одного года** после паузы, с сохранением
данных и конфигурации. Фактическую доступность операции проверять в Dashboard;
дата появления URL в Git не является датой паузы.
[Документация Supabase](https://supabase.com/docs/guides/platform/free-project-pausing).

Дождаться Healthy, проверить DNS, HTTPS и Auth. Если Dashboard вместо возобновления
предлагает создание проекта или перенос бэкапа, остановиться: создание новой БД
требует отдельного подтверждения владельца.

### Dashboard показывает Active/Healthy, а DNS по-прежнему NXDOMAIN

Ничего не удалять, не приостанавливать активный проект ради эксперимента и не
подставлять чужой IP в hosts. Проверить project ref в General settings и журналы
операций. Подготовить обращение Supabase Support о восстановлении DNS/маршрутизации
**существующего** проекта. Сообщение без секретов подготовлено ниже, но не отправлено.

### Проект не найден или доступ запрещён

Сначала проверить прежний аккаунт, организацию, владельца и перенос проекта.
При необходимости запросить у Supabase Support проверку владения и состояния ref.
Отказ API по правам и пустой список проектов не равны подтверждению удаления.
Если приостановленный проект вышел за окно восстановления, проверить предлагаемые
Dashboard выгрузки database backup и Storage; сохранить доступные копии до решения
о переносе. Наличие выгрузок не гарантируется.
[Документация восстановления](https://supabase.com/docs/guides/platform/upgrading).

### Удаление подтверждено владельцем или Supabase

По документации удаление проекта необратимо и удаляет также резервные копии и
конфигурацию; штатное восстановление удалённого проекта недоступно. Удаление
убирает и DNS-записи, но обратное утверждение по одному NXDOMAIN делать нельзя.
Искать уже существующие внешние резервные копии, SQL-экспорты и Storage-архивы.
Создание нового проекта и импорт возможны только после отдельного согласования.
Без копии прежних Auth-данных обещать сохранность аккаунтов и паролей нельзя.
[Документация удаления](https://supabase.com/docs/guides/platform/delete-project).

## Безопасный порядок восстановления авторизации

1. Подтвердить владельца и состояние существующего проекта. Восстановить его
   доступность по подходящему сценарию выше, не создавая параллельную базу.
2. После получения доступа исследовать существующие схемы, Auth identities,
   количество пользователей, профили, RLS, триггеры, Storage, Edge Functions,
   URL redirects, SMTP и список имён секретов. Не получать пользовательские
   пароли и не выводить токены/содержимое секретов.
3. Сохранить доступные полные резервные копии БД, включая Auth и прикладные схемы,
   и Storage; отдельно зафиксировать конфигурацию и политики. Убедиться в составе
   копии и доступном способе восстановления. Хранить вне Git и публичных Pages.
   Сохранить UUID пользователей, хэши паролей, профили, связи и provider subjects.
4. Сопоставить существующую схему с подготовленным
   `supabase/sql/auth-hardening.sql`. Он **не применён** и требует проверки
   совместимости и пробного выполнения на согласованном окружении. Не очищать
   `auth.users`, не пересоздавать профили, не менять UUID и не объединять аккаунты
   только по неподтверждённому e-mail.
5. Проверить Email Auth, подтверждение почты, правила пароля, production SMTP,
   лимиты и точные HTTPS redirects. Site URL: `https://palanart.github.io/`;
   redirects: `/user.html`, `/user.html?recovery=1`, `/artist.html` на этом домене.
6. Проверить владение приложениями Telegram, VK ID, MAX и Яндекс ID. Секреты
   провайдеров хранить в Supabase Edge Function Secrets; публиковать только
   допустимый public/publishable key. Развернуть подготовленные функции после
   проверки схемы, одноразовых state, CORS, подписей и привязки к существующему UUID.
   Точные callback URL и список переменных есть в
   [основном отчёте](palanart-auth-recovery-2026-10-26.md#настройки-провайдеров).
7. Провести контролируемые реальные тесты: регистрация → письмо → подтверждение →
   кабинет → выход → повторный вход; неверный пароль; существующий e-mail;
   восстановление → письмо → смена пароля. Для каждого соцсервиса — реальный вход,
   отмена, повторный callback, привязка и проверка отсутствия второго профиля.
   Учётные записи теста не удалять без согласования.
8. Проверить RLS с владельцем профиля и другим пользователем, регрессии каталога,
   кабинетов исполнителя/заказчика и админ-панели. После публикации повторить
   реальные сценарии на `https://palanart.github.io/user.html` и зафиксировать
   результат отдельно для каждого способа. Успешная кнопка/локальный тест не равны
   успешной авторизации.

## Независимые исправления интерфейса

Убраны изображения совещаний и большой рекламный блок над формой заказчика.
Вход по e-mail находится первым, четыре социальных способа вынесены в общий
блок. Восстановление заменяет форму входа на том же месте; возврат восстанавливает
фокус. Старая ошибка очищается при новой попытке. При сетевой ошибке соцсервиса
больше нет ложного совета воспользоваться e-mail на том же недоступном backend.
Адреса ресурсов и service worker обновлены для доставки правок в браузер.

Локальная браузерная проверка подтвердила: формы без изображений совещаний,
четыре общие социальные кнопки, замена входа восстановлением на том же месте,
возврат со ссылкой «Уже есть аккаунт?» к видимой форме и фокусу e-mail, ручной
ввод города. На ширинах 320 и 390 px горизонтального переполнения нет.
MAX и Telegram возвращают сетевую ошибку и разблокируют кнопки; старая ошибка
исчезает при новой попытке. Это проверка интерфейса, а не успешной авторизации.

Полная работоспособность регистрации и входа по-прежнему **не подтверждена**.
Сохранность серверных данных нельзя подтвердить до доступа и проверки резервной копии.
