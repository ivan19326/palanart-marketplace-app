## Подтверждённые изменения Supabase

[Проект](https://supabase.com/dashboard/project/oimwiyncaxffcijqtmzf)
доступен через подключённый API и авторизованный Dashboard. Вход в Dashboard
выполнен через существующий аккаунт ChatGPT, связанный с выбранной организацией.
Браузерная авторизация не требовалась для чтения проекта/SQL, но позволила
настроить Auth, для которого подключённый API не предоставляет отдельной команды.

В [URL Configuration](https://supabase.com/dashboard/project/oimwiyncaxffcijqtmzf/auth/url-configuration)
сохранены Site URL `https://palanart.github.io/` и четыре точных redirect URL:

- `https://palanart.github.io/user.html`
- `https://palanart.github.io/user.html?recovery=1`
- `https://palanart.github.io/artist.html`
- `https://palanart.github.io/artist.html?recovery=1`

Подтверждение e-mail включено, анонимный вход выключен. Включён штатный Manual
Linking для привязки провайдеров из уже проверенного аккаунта. Реальная привязка
другого провайдера остаётся в плане испытаний после получения его настроек.

Сервер отклоняет пароли короче 10 символов и требует латинскую букву и цифру.
Это проверено реальными запросами signup: короткий пароль, только цифры,
только буквы и пароль без латинской буквы получили HTTP 422 `weak_password`.
У формы и восстановления те же правила; устранено прежнее несоответствие,
при котором форма принимала пароль без латинских букв, отклоняемый сервером.

## Google: существующее приложение и реальные данные

Использован существующий Google Cloud проект `palanart-auth`, клиент
[Palanart Web](https://console.cloud.google.com/auth/clients/439595831504-i7vtvdqlk96cu7irvf0pu9rvgmbsbcb9.apps.googleusercontent.com?project=palanart-auth).
Клиент Palanart Outreach Agent не изменялся.

- Добавлен origin `https://palanart.github.io`; прежний origin сохранён.
- Добавлен callback `https://oimwiyncaxffcijqtmzf.supabase.co/auth/v1/callback`;
  прежний callback сохранён.
- Дополнительный Client Secret создан с отдельного подтверждения владельца.
  Прежний secret остаётся активным. Значение нового секрета сохранено только
  в защищённых Auth-настройках Supabase, в публичных файлах его нет.
- Проверен HTTP 302 от настоящего authorize endpoint: правильные Client ID и
  callback; запрашиваются только `email` и `profile`, без доступа к Gmail.
- Audience существующего приложения: External, In production. Настройки
  публикации и общие scopes проекта не менялись. В консоли есть уведомление
  о проверке приложения для неутверждённых sensitive/restricted scopes;
  вход PALANART таких scopes не запрашивает.

На основном домене получена настоящая Supabase-сессия после Google OAuth.
Кабинет открылся под подтверждённой Google-учётной записью владельца. После
выхода и перезагрузки кабинет закрыт. Повторный Google-вход снова открыл кабинет.
SQL-проверка подтвердила неизменный UUID, один Auth-профиль и одну строку
`palanart_profiles`; e-mail подтверждён, provider — `google`, роль — `client`.
Фиктивные сессии и локальные пароли для этой проверки не использовались.

## Почта: подготовлено, требуется личный этап

Владелец выбрал Gmail отправителем. На странице
[SMTP Settings](https://supabase.com/dashboard/project/oimwiyncaxffcijqtmzf/auth/smtp)
подготовлены имя PALANART, выбранный Gmail, `smtp.gmail.com`, порт 587 и username.
Пароль не заполнен, конфигурация SMTP не сохранена. В UI есть предупреждение,
что персональный почтовый сервис может уступать транзакционному по доставляемости.

Google запросил личное подтверждение аккаунта на странице
[паролей приложений](https://myaccount.google.com/apppasswords).
Владелец должен подтвердить вход, создать пароль приложения PALANART SMTP,
вставить его прямо в Password в Supabase и сохранить настройки. Пароли не нужны
в чате или репозитории. Для паролей приложений Google требует двухэтапную
аутентификацию. Обычный пароль Google в SMTP не используется.

После этого обязательны реальные письма подтверждения и восстановления,
регистрация по e-mail, выход/повторный вход и смена пароля. До подтверждения
доставки и этих сценариев флаг отправки писем не включать.
